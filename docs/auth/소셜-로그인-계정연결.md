# 구글·애플 로그인과 계정 연결

기존 `/api/v1/auth/login/google`, `/auth/social/register`, `/auth/reissue`, `/auth/logout`과 탈퇴 계약을 유지한다. 모든 오류는 `{code,message}` 형식이다. 소셜 공급자 식별자는 이메일이 아닌 검증한 `sub`를 사용한다. 이메일·휴대폰 일치로 계정을 자동 병합하지 않는다.

## 앱 API 계약

| 요청 | 본문 | 응답 |
|---|---|---|
| POST `/api/v1/auth/apple/challenge` | 없음 | `{challengeToken,nonce,expiresInSeconds:300}` |
| POST `/api/v1/auth/login/apple` | `{identityToken,authorizationCode,challengeToken,name?}` | 기존 구글과 같은 `LOGIN` 또는 `SIGNUP_REQUIRED` |
| GET `/api/v1/users/me/login-methods` | 없음 | `{hasPassword,methods:[{provider,status}]}` |
| POST `/api/v1/users/me/login-methods/sms/send` | 없음 | 204 |
| POST `/api/v1/users/me/login-methods/sms/verify` | `{code}` | `{verificationToken,expiresInSeconds:300}` |
| POST `/api/v1/users/me/login-methods/google` | `{idToken,verificationToken}` | 204 |
| POST `/api/v1/users/me/login-methods/apple/challenge` | 없음 | 로그인용과 같은 응답, 현재 회원과 연결 목적에 묶임 |
| POST `/api/v1/users/me/login-methods/apple` | `{identityToken,authorizationCode,challengeToken,verificationToken}` | 204 |
| POST `/api/v1/auth/apple/notifications` | `{payload}` | 204 |

`/users/me/**`에는 Bearer 인증이 필요하다. 연결 SMS는 서버에 등록된 휴대폰으로만 보낸다. 앱은 번호를 보내지 않는다. 연결용 SMS와 가입용 SMS는 별도 네임스페이스이고 발송량·쿨다운은 공유한다. 검증 코드는 기존 3분·최대 5회, 연결 증표는 5분이다.

Apple SDK 요청의 `nonce`에 서버 응답 `nonce`를 그대로 넣는다. 클라이언트가 임의 생성한 nonce를 서버에 제출하는 방식은 지원하지 않는다. 로그인과 연결 challenge를 교차 사용할 수 없다. challenge는 검증을 시작할 때 소진되므로 인증 실패·통신 오류 뒤에는 새 challenge와 새 Apple 인증 코드를 받는다.

소셜 가입 대기표는 기존 10분이다. 신규 Apple 계정의 검증 토큰에 이메일이 없으면 USER401로 실패한다. 기존 회원은 이메일 없이 subject로 로그인할 수 있다. `name`은 표시용 입력이고 신원 증거가 아니다. Apple 개인정보 보호 이메일도 그대로 저장한다.

같은 회원·같은 공급자·같은 계정 연결은 새 유효 재인증 증표로 반복해도 성공한다. 성공한 증표 재사용은 USER406이다. 다른 회원 소유 계정이나 같은 공급자의 다른 계정으로 교체하려는 요청은 USER405이며, 실패한 연결의 SMS 증표는 롤백되어 유효기간 안에 재사용할 수 있다.

| 코드 | HTTP | 의미 |
|---|---:|---|
| USER401 | 401 | 공급자 토큰·코드 검증 실패, 신규 가입에 이메일 없음 |
| USER402 | 401 | 소셜 가입 대기표 만료 |
| USER403 | 409 | 이미 가입된 소셜 계정 |
| USER404 | 503 | 공급자·인증 저장소 사용 불가 |
| USER405 | 409 | 다른 계정 연결 또는 공급자 계정 교체 충돌 |
| USER406 | 401 | 연결 재인증 증표 만료·재사용·다른 회원 증표 |
| USER407 | 401 | Apple challenge 만료·재사용·용도/회원 불일치 |

## 저장과 동시성

Flyway V43은 기존 `social_user.user_id`와 식별자를 보존하면서 독립 identity PK를 추가한다. `(user_id,social_type)`와 `(social_type,social_id)` UNIQUE로 복수 수단과 소유권을 보장한다. 상태는 `ACTIVE`/`REVOKED`이다. 기존 KAKAO/NAVER 데이터는 유지하며 신규 앱 API는 GOOGLE/APPLE만 노출한다.

연결·재발급·탈퇴·로컬 로그인·비밀번호 재설정은 사용자 행부터 잠근다. Apple 계정 단위 작업은 추가로 `apple_grant_lock`의 subject 행을 잠근다. 공급자 코드 교환과 철회는 같은 subject에서 직렬화한다. 철회 작업은 사용자 행을 역순으로 잠그지 않는다.

Apple refresh token은 기존 FieldCipher(AES-GCM)로 암호화하여 저장한다. 코드 교환 직후 별도 트랜잭션으로 PENDING 행을 커밋하므로 이후 가입·연결 오류가 나도 정리할 참조가 남는다. 가입/연결 성공 시 ACTIVE로 바꾸고, 탈퇴 트랜잭션에서 REVOKE로 바꾼다. DB 행 자체가 철회 outbox이며 스케줄러가 1분마다 20건씩 처리한다. 실패 시 최대 하루 간격으로 계속 재시도하며 로그에는 참조 ID와 시도 횟수만 남긴다.

중단된 가입의 PENDING는 10분 뒤 철회 대상이다. 같은 subject에 ACTIVE 또는 새 유효 PENDING가 있으면 오래된 토큰만 로컬 삭제하여 새 동의를 원격 철회하지 않는다. 새 인증으로 활성화한 경우 구버전 활성 토큰도 로컬 삭제한다. 일회성 증표는 SHA-256 해시만 저장하고 만료 행을 정리한다.

## Apple 알림

Apple 공개키로 RS256 서명·issuer·허용 audience·iat를 검증한다. event_time은 공식 계약의 초 단위로 읽되, 밀리초로 전달되는 사례 보고에 대비해 1e11 이상인 값은 밀리초로 해석한다. 7일보다 오래되거나 30초 넘게 미래인 알림은 거절한다. events 객체와 JSON 문자열 표현을 모두 지원한다. jti 중복은 한 번만 처리한다.

`consent-revoked`, `account-deleted`(및 같은 뜻으로 보고된 표기 `account-delete`)는 해당 Apple 수단만 REVOKED로 바꾸고 모든 기존 모여타 refresh/access 세션을 무효화한다. 구글·비밀번호 수단은 유지한다. 새 인증 iat보다 오래된 알림은 재동의 뒤 지연 도착한 것으로 보고 무시한다. subject별 최신 철회 시간을 저장해 알림 도착 전에 검증한 PENDING 토큰도 이후 가입·연결에서 활성화하지 못하게 한다. 재동의한 Apple 로그인은 다시 ACTIVE로 만든다. email-enabled/disabled는 로그인 수단을 비활성화하지 않는다.

근거: [Apple 사용자 검증](https://developer.apple.com/documentation/signinwithapple/verifying-a-user), [Apple 계정 변경 알림](https://developer.apple.com/documentation/signinwithapple/processing-changes-for-sign-in-with-apple-accounts).

## 설정과 운영 준비

- `APPLE_CLIENT_IDS`: 허용 네이티브 Bundle ID/Service ID 목록. 비어 있으면 fail-closed.
- `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`: 서버 토큰 교환용 설정. 키는 PKCS#8 P-256 PEM이며 실제 줄바꿈 또는 `\\n`을 지원한다. 저장소·HTTP 파일·PR 본문에 실키를 넣지 않는다.
- `FIELD_ENCRYPTION_KEY`: 기존 암호화 키. Apple 토큰을 복호화할 수 있도록 기존 키를 유지한다.
- 공개 알림 URL: 배포 대상 HTTPS 도메인의 `/api/v1/auth/apple/notifications`.
- `moyeota.apple.base-url`: 기본 `https://appleid.apple.com`. 로컬 테스트에서만 모의 서버 주소로 재정의한다.

운영 적용 전 사용자가 Apple Developer 로그인·Sign in with Apple 활성화·키 발급·알림 URL 설정을 완료해야 한다. DB 백업 뒤 V43 적용과 새 애플 환경변수를 포함한 배포를 수행한다. 기존 Google 설정과 비밀번호 로그인은 유지된다. 이 작업에서는 push·PR 생성·운영 배포를 수행하지 않는다.

## 검증 범위

- `AppleClientTest`: 로컬 HTTP 서버, 실제 테스트 RSA/EC 키, JWT 서명·aud·exp·nonce·코드 subject 불일치, 코드 실패/503, 철회 실패.
- `SocialStatePersistenceTest`: H2 저장·암호화·증표 목적/소유자/만료·롤백·동시 소비·철회 재시도.
- `SocialAccountHttpTest`: 실제 MVC/보안 필터/서비스/DB로 Apple 가입→Google 연결→같은 회원 로그인→재발급→탈퇴 및 알림 처리. 외부 공급자와 SMS/Redis 경계만 모의 처리한다.
- 실제 Apple/Google 계정 SDK, 실키 및 운영 공급자 통신, 실기기 간 동일 UUID 검증은 별도 수동 검증이 필요하다.

최종 로컬 검증(2026-11-15): 본체 1,826개 테스트 통과 및 bootJar 성공. 실제 PostgreSQL/Redis 통합 suite는 서비스 포트 미준비로 건너뛰었으며, 실기기 SDK 검증과 구분한다. 자세한 결과는 [PR 초안](소셜-로그인-PR-초안.md)에 기록했다.
