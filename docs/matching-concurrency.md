# DB 사용자 잠금 기반 매칭 동시성 제어

같은 사용자의 방 생성·참가를 사용자 행 잠금으로 직렬화한다. 서로 다른 사용자들의 정원 경쟁은 기존 방 행 잠금으로 보호한다.

## PAAR — 문제·분석·실행·결과

- 문제: 두 요청이 모두 “참여 중인 방 없음”을 확인하면 다른 방 잠금은 서로를 막지 못했다.
- 분석: 이 서비스의 판정과 저장은 하나의 PostgreSQL writer에서 끝난다. 별도의 락 서버 없이 DB 사용자 행을 공통 직렬화 지점으로 쓸 수 있다. 방의 @Version만으로는 다른 방 사이 사용자 중복을 해결할 수 없다.
- 실행: 사용자 모듈 공개 인터페이스 `MatchingMemberLock`을 통해 사용자 행을 잠근 뒤 참가 여부 확인→방 잠금→참가 저장을 한 트랜잭션에서 실행한다. 현재 참여 PK, 외부 경로 호출 분리, 유한 대기를 공통 적용한다.
- 결과: 전체 테스트 450개 통과(성능 실험 포함). PostgreSQL에서 오류를 먼저 재현하고 수정 후 중복/정원/롤백/재참가를 검증했다. 자세한 실측값은 아래 비교표를 참고한다.

## 잠금 흐름과 장단점

```text
경로 조회(방 생성만, 트랜잭션 밖)
→ DB 트랜잭션 시작
→ 사용자 행 잠금
→ 기존 참여 확인
→ 방 행 잠금(참가 시)
→ 방/현재 참여 저장
→ 커밋 또는 롤백과 함께 잠금 해제
```

장점: 쓰기 DB 자체가 잠금과 커밋의 수명을 관리한다. Redis 소유권 갱신/만료/연결 장애라는 추가 실패 모드가 없다. 여러 애플리케이션 인스턴스도 같은 DB 행 잠금에 참여한다. Redis가 다른 기능에 사용되더라도 매칭의 사용자 잠금에는 필요하지 않다.

비용: 같은 사용자 요청을 기다리는 동안 DB 연결과 트랜잭션을 점유한다. 사용자 행의 다른 갱신과 경합할 수 있다. 여러 행에 접근하므로 락 순서를 유지해야 하며, 대기 초과 응답을 처리해야 한다. DB가 다중 독립 writer로 분리된다면 이 전제를 다시 검토해야 한다.

## 문제와 보장 범위

같은 사용자가 서로 다른 방에 동시에 참가하면 기존의 `참여 여부 SELECT → 방 SELECT FOR UPDATE → INSERT`는 두 요청을 모두 통과시킬 수 있다. 방 잠금은 서로 다른 방 사이의 사용자 중복을 막지 못한다. 반대로 사용자별 유일성만으로는 서로 다른 사용자가 같은 방의 정원을 초과하는 것을 막지 못한다.

보장할 규칙은 ① 사용자당 진행 중인 참여 1개 ② 방 정원 준수 ③ 참가 실패 시 방/현재 참여 함께 롤백 ④ 퇴장·취소·종료 후 다시 참가 가능이다. Redis 락이 만료되어 입장 작업이 겹쳐도 DB 제약조건이 ①을 보장한다. 이 PR은 채팅 이벤트 순서 역전, HTTP 요청 식별자 기반 멱등 응답, 스케줄러의 만료 재확인까지 변경하지 않는다.

## 공통 설계

- `MatchingAdmission`은 방 생성·참가의 사용자별 직렬화 경계다. 두 PR은 이 구현만 DB/Redis로 바꾼다. 단위 테스트에서는 이 경계만 인라인으로 대체한다.
- 네이버 경로 조회/Redis 경로 캐시는 사용자 잠금과 DB 트랜잭션 밖에서 실행한다. 캐시 미스나 외부 API 지연으로 잠금이 길어지지 않게 한다. 중복 사용자여도 이 선행 조회가 발생할 수 있다는 비용은 남는다.
- 입장 트랜잭션은 명시적으로 `READ_COMMITTED`, 타임아웃 5초다. PostgreSQL `SET LOCAL lock_timeout = '2s'`로 사용자/방/제약조건 충돌의 실제 DB 락 대기도 제한한다. 연결 실패나 커밋 통신 장애까지 절대 5초를 보장하는 설정은 아니다.
- 사용자 락 획득 후 참가 여부를 다시 조회하고, 참가 대상 방을 잠근다. 사용자 → 방 순서를 통일한다. 퇴장·종료는 기존 방 잠금만 사용하며, 방을 잡은 상태에서 사용자 잠금을 추가 획득하지 않는다.
- `active_match_participation`의 `user_id` PK가 현재 참여의 최종 방어선이다. 종료된 방의 과거 이력은 `user_match_room`에 유지한다. 과거 이력에 사용자 전체 unique 또는 `(사용자, 종료여부)` unique를 추가하지 않는다.
- `PartyJpa.save`가 방/멤버를 flush한 뒤 동일한 트랜잭션/연결에서 현재 참여를 동기화한다. INSERT로만 새 사용자를 점유하고 PK 충돌을 409로 변환한다. merge/upsert로 타인의 기존 점유를 덮어쓰지 않는다.
- 새 방 생성, 참가, 퇴장, 마지막 멤버 퇴장, 사용자 종료, 자동 종료, 배차 실패, 운행 완료가 같은 저장 경계를 거친다. 닫힌 방은 현재 참여를 해제하지만 이력은 남긴다.
- 상위 트랜잭션 안에서 입장 경계를 호출하면 즉시 실패시킨다. 외부 트랜잭션의 커밋보다 락이 먼저 해제되는 잘못된 사용을 허용하지 않는다.

### 오류와 재시도 의미

| 상황 | 응답/동작 |
| --- | --- |
| 이미 진행 중인 방이 있음/최종 PK 충돌 | `409 ALREADY_JOINED_OTHER_PARTY` |
| 마감된 방/정원 초과 | 기존 `PARTY_CLOSED` / `PARTY_FULL` |
| 락 경합·DB 잠금 대기 초과 | `409 MATCHING_BUSY` |
| Redis 방식에서 잠금 서비스 연결 실패 | `503 MATCHING_LOCK_UNAVAILABLE`; 잠금 없는 우회 금지 |

응답 유실 후 재요청하면 기존 참가를 다시 만들지는 않지만, 이전 성공 응답을 재생하지는 않는다. 기존 API처럼 409가 올 수 있으므로 현재 상태를 조회해야 한다. HTTP 멱등 키/결과 저장은 별도 과제다. 서버가 무제한 자동 재시도하지 않으며, 클라이언트 재시도가 필요하면 제한된 횟수와 지연을 둔다.

## 대안 비교 — DB, Lettuce 직접 구현, Redisson, ZooKeeper

DB와 Redisson은 각각의 대안 브랜치에서 구현·테스트·측정했다. Lettuce 직접 구현은 Redis 브랜치의 테스트 전용 대안으로 구현·측정했다. ZooKeeper와 Redlock은 설계/문서 검토만 수행했다.

### 선택지를 같은 수준으로 정리하기

Lettuce와 Redisson은 Redis 클라이언트/라이브러리 선택이고, ZooKeeper는 다른 조정 시스템을 도입하는 선택이다. Redis 분산 락 구현법이 둘뿐이라는 뜻은 아니다. 특히 Redisson(라이브러리)과 Redlock(여러 독립 Redis 노드의 과반수 획득을 사용하는 알고리즘)은 다르다. 현재 코드는 단일 주소의 Redisson RLock이며 Redlock 구현이 아니다.

| 관점 | DB 비관적 잠금 | Lettuce + SET NX PX 직접 구현 | Redisson RLock | ZooKeeper 임시 순차 노드 |
| --- | --- | --- | --- | --- |
| 직렬화 지점 | 같은 DB 사용자 행 | 같은 Redis 사용자 키 | 같은 Redis 사용자 키 | 같은 잠금 경로의 노드 순서 |
| 대기 방식 | DB 잠금 대기 | 직접 설계: 즉시 실패 또는 제한된 백오프/지터 재시도 | Pub/Sub 알림 및 재획득 시도 | 바로 앞 순번 노드의 삭제 감시 후 재확인 |
| 수명 | 트랜잭션 커밋/롤백 | 고정 TTL 또는 직접 소유권 확인 갱신 | watchdog 갱신 또는 명시적 leaseTime | 세션 유지/만료 및 노드 삭제 |
| 안전 해제 | DB가 관리 | 요청 토큰 비교와 삭제를 Lua 등으로 원자 수행 | 라이브러리의 소유자 검사 | 자신의 노드 삭제; 세션 상태도 처리 |
| 재진입 | 트랜잭션 안의 행 잠금 | 토큰/카운트/호출 규칙을 직접 설계 | 지원 | 사용하는 레시피/라이브러리에 따라 다름 |
| DB 연결 대기 비용 | 사용자 락 대기 중에도 연결 사용 | 획득을 DB 트랜잭션 앞에 두면 대기 중 미사용 | 획득 대기 중 미사용 | 획득을 DB 트랜잭션 앞에 두면 대기 중 미사용 |
| 추가 비용 | 사용자 행 경합, DB 연결/트랜잭션 점유 | 토큰·TTL·안전 해제·재시도·갱신 직접 관리 | 의존성/연결 풀/구독/갱신 작업 | 앙상블 운영, 합의 통신, 세션·watch·재연결 처리 |
| 정합성의 최종 방어 | DB 트랜잭션 + 현재 참여 PK + 방 잠금 | 동일 DB 방어 필요 | 동일 DB 방어 유지 | 외부 DB 기록에는 동일 DB 방어 또는 검증 가능한 fencing 필요 |
| 현재 평가 | 실제 구현·실측 | 테스트 전용 구현·실측 | 실제 구현·실측 | 설계 비교만 |

Lettuce 자체가 spin lock인 것은 아니다. 앱이 어떤 획득 재시도 루프를 구현하느냐에 따라 달라진다. Redisson RLock이 Pub/Sub를 쓴다고 획득 재시도나 통신 비용이 사라지는 것도 아니다. FIFO가 필요한 요구사항은 일반 RLock과 FairLock을 별도로 비교해야 한다.

### Lettuce 직접 구현의 검증 기준

직접 구현의 최소 계약은 아래와 같다. 아래는 설계 의사 코드이며 현재 서비스에 연결된 실행 코드가 아니다.

```text
요청마다 고유 token 생성
→ SET matching:user:{id} token NX PX ttl 을 단일 명령으로 시도
→ 실패 시 획득 마감 시간 안에서만 백오프 + 지터 재시도
→ 성공 후 DB 트랜잭션 실행 및 커밋/롤백 완료
→ Lua에서 값이 내 token일 때만 DEL
```

SETNX 뒤 별도 EXPIRE를 호출하면 중간 장애 시 무기한 락이 남을 수 있다. GET으로 소유자를 확인한 뒤 별도 DEL하는 것 역시 둘 사이에 새 소유자가 생길 수 있어 안전하지 않다. 갱신도 토큰 확인과 TTL 연장을 원자적으로 처리해야 한다. 고정 TTL만 쓰는 버전과 watchdog 갱신 버전은 같은 보장 수준이 아니므로 성능 숫자만 나란히 놓지 않는다.

직접 구현에서 고려할 계약은 ① 서로 다른 클라이언트의 상호 배제 ② 만료된 A가 새 소유자 B의 락을 지우지 못함 ③ 획득 실패 시 DB 진입 없음 ④ 인터럽트/예외/해제 실패 ⑤ 갱신 실패 후 DB PK 방어를 같은 시나리오로 검증하는 순서가 적절하다. 그 뒤 Redis 명령 수, p95, 관측 DB 연결 수와 구현 복잡도를 Redisson과 비교한다. Redis 브랜치에는 테스트 전용 대안 어댑터를 추가했다. 고정 TTL 버전이라 갱신 실패 자체는 구현·검증하지 않았으며, 잠금 중첩 상태에서 DB PK 방어를 공통 테스트로 검증했다. 실제 검증 범위와 미계측 항목은 아래 추가 검증 절에 구분했다.

### ZooKeeper를 검토할 때 달라지는 문제

대표 락 레시피는 ephemeral sequential 노드를 만들고 가장 작은 순번이 잠금을 소유하게 하며, 대기자는 바로 앞 노드만 감시한다. 삭제 알림 이후에도 현재 순서를 다시 확인해야 한다. 생성은 성공했지만 응답이 유실된 경우 중복 노드를 만들지 않도록 복구도 고려한다.

세션 기반이라는 이유로 프로세스 종료를 즉시 알아내는 것은 아니다. 서버 측 세션 만료 판단까지 시간이 필요하고, 연결이 끊긴 클라이언트는 자신의 세션이 만료됐다는 사실을 뒤늦게 알 수 있다. 세션을 잃어도 실행 중인 Java 코드가 자동으로 취소되거나 외부 DB 쓰기가 자동 롤백되지는 않는다. 이전 소유자의 늦은 쓰기를 금지하려면 보호 대상이 순서/세대 토큰을 검증해야 한다. 순차 번호도 잠금 경로 재생성 등을 포함한 수명 설계 없이 영구적인 fencing 토큰으로 간주하면 안 된다.

ZooKeeper가 이미 운영 중이거나 잠금 이외의 리더 선출·그룹 멤버십·세션 기반 조정이 함께 필요한 경우 검토 가치가 높다. 현재 모여타처럼 동일 PostgreSQL의 참가 상태를 보호하는 목적만으로 새 앙상블을 도입할 이점은 아직 입증하지 않았다. 단일 서버 테스트만으로 합의/장애 전환의 이점을 검증했다고 할 수 없으므로 실제 비교에는 다중 노드 구성과 세션 만료·연결 단절 시험이 필요하다.

### 이번 비교의 권장 범위와 PAAR 연결

- DB PR: DB 사용자 잠금으로 해결 가능한 범위, 커넥션 점유 비용과 실제 결과를 설명한다.
- Redis PR: 직접 구현 시 필요한 계약과 Redisson이 대신하는 기능을 분석한다. Lettuce 직접 구현과 Redisson을 동일 서비스 시나리오로 검증·측정하고 수명 보장 차이를 명시한다.
- 공통 대안 검토: ZooKeeper와 Redlock을 자동으로 더 좋은 해법으로 취급하지 않고 운영 전제·장애 가정·추가 비용을 비교한다.
- 결과: 실제 측정한 DB/Lettuce/Redisson 결과만 수치로 쓰고, ZooKeeper/Redlock은 미구현·미측정임을 명시한다.

PAAR에서 분석의 깊이는 라이브러리 개수가 아니라 요구사항→후보별 보장 범위→실험→선택의 연결에서 나온다. 원격 게시 전 이 대안 비교를 PR 본문 분석 부분에도 반영할 수 있다.

공식 근거: [Redis 단일 인스턴스 락과 안전 해제](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/), [Redisson 락 종류와 watchdog](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/), [ZooKeeper 잠금 레시피](https://zookeeper.apache.org/doc/r3.7.2/recipes.html), [ZooKeeper 세션 만료](https://zookeeper.apache.org/doc/r3.9.0/zookeeperProgrammers).

## Lettuce 직접 구현 추가 검증과 선택

Redis 브랜치의 `src/test/java/.../matching/infrastructure`에 실험 전용 `LettuceMatchingAdmission`과 공통 시나리오를 상속하는 `LettuceMatchingConcurrencyTest`를 추가했다. Spring Data Redis의 Lettuce 연결로 `SET NX PX`를 실행하고, 요청마다 UUID 토큰을 발급한다. 최대 2초 동안 5~50ms 범위의 증가하는 백오프와 지터로 재시도하며, 토큰 비교·삭제 Lua로 해제한다. 진행 중인 Redis 명령의 타임아웃은 1초여서 전체 호출 시간이 획득 대기 예산 2초를 넘을 수 있다. 스레드 인터럽트를 보존하고 획득 장애 시 DB로 우회하지 않는다.

고정 TTL 30초이며 watchdog·재진입·공정성을 구현하지 않는다. DB 트랜잭션 제한 5초가 있어도 JVM 정지나 네트워크 장애까지 포함한 벽시계 실행 시간을 보장하지 않는다. TTL 경과 후에도 옛 작업자가 쓸 수 있으므로 DB 현재 참여 PK와 방 잠금을 유지한다. Redisson의 자동 갱신과 같은 수명 보장은 아니며 아래 측정에는 TTL 갱신 주기를 넘는 장시간 작업이 없다.

운영 코드에는 Redisson 어댑터 하나만 등록된다. Lettuce 실험은 테스트 소스와 별도 키 접두사로 격리했으므로 두 어댑터를 서로 다른 운영 노드에 섞어 배포해서는 안 된다. 실험용 Lettuce 연결은 로컬 무인증 Redis를 기본으로 하며 `MATCHING_EXPERIMENT_REDIS_HOST`, `MATCHING_EXPERIMENT_REDIS_PORT`로 변경한다. 운영 TLS·인증·클러스터 지원 대안으로 제공하는 코드가 아니다.

실제 PostgreSQL·Redis에서 같은 동시 생성/참가, 마지막 자리 경쟁, 다른 사용자 병렬 진행, 롤백, 참여 해제 및 재가입, 잠금 중첩 시 DB 제약 방어를 검증했다. 실제 Redis TTL 만료 후 A의 Lua 해제가 B의 잠금을 삭제하지 않음을 확인했다. 단위 테스트로 연결 실패·획득 대기 초과·인터럽트와 커밋/롤백 이후 해제 실패를 검증했다. Redis 브랜치 전체 473개 테스트가 성공했고 실패·오류·건너뜀은 모두 0개다(성능 실험 활성화).

아래는 추가 실행에서 Lettuce와 Redisson을 순차 측정한 각 3회 통계의 중앙값이다. 앞의 DB/Redisson 표는 이전 실행을 보존한 것이므로 실행 간 수치를 혼합하지 않는다. 부하 크기·DB 풀·서비스 호출 및 정상 거절 포함 조건은 동일하다.

| --- | --- | ---: | ---: | ---: | ---: |
| 동일사용자 | Lettuce 직접 구현 | 1.62 | 159.53 | 455.1 | 1 |

동일 사용자 경합의 p95는 Lettuce 159.53ms, Redisson 114.73ms였다. 작은 표본과 실행 순서의 영향을 포함한 로컬 관측이며 보편적인 성능 순위는 아니다. 특히 낮은 p50과 높은 p95가 함께 나타나므로 중앙 지연만으로 사용자 경험을 평가하지 않는다. Redis 명령 수·CPU·공정성·다중 호스트 장애 전환은 계측하지 않았다.

**선택:** 현 MVP는 단일 PostgreSQL의 참가 정합성이 목적이므로 DB 방식을 우선 추천한다. Redis 방식은 같은 사용자의 경합이 DB 연결을 점유하는 문제가 실제로 확인될 때의 대안이다. 그 경우 운영 구현은 Redisson을 선택한다. 이번 수치만이 아니라 자동 갱신·소유권 검사·알림 대기를 직접 유지보수하는 부담을 줄이는 것이 선택 근거다. ZooKeeper와 Redlock은 운영 전제와 장애 가정을 문서로 비교했으며 이번에는 구현하거나 성능을 측정하지 않았다.

## 배포와 대안 PR 관계

두 PR은 같은 develop 커밋에서 출발한 대체안이다. 둘을 그대로 함께 병합하지 않는다. 같은 V7 마이그레이션과 공통 클래스가 있으며, 입장 구현체도 하나만 있어야 한다. 하나를 채택한 뒤 다른 아이디어가 필요하면 선택적으로 이식한다. 다른 기능 PR이 먼저 V7을 사용하면 미적용 상태의 이 마이그레이션 번호를 조정해야 한다.

V7은 기존 활성 참여를 backfill한다. 중복이 있으면 마이그레이션이 실패하므로 배포 전에 아래 결과를 확인하고 서비스 정책에 따라 정리한다. 임의로 한 방을 고르거나 데이터를 삭제하지 않는다. 기존 노드가 새 제약 테이블 없이 쓰는 혼재 기간을 방지하려면 생성·참가 쓰기를 중단하고 마이그레이션/새 코드를 적용한 뒤 재개한다.

```sql
SELECT m.user_id, count(*), array_agg(m.match_id ORDER BY m.match_id)
FROM user_match_room m JOIN match_room p ON p.id = m.match_id
WHERE p.status IN ('ACTIVE', 'COMPLETED', 'MATCHING', 'DRIVER_ASSIGNED', 'IN_RIDE')
GROUP BY m.user_id HAVING count(*) > 1;
```

현재 참여 테이블은 애플리케이션 저장 경계를 통해 일관성을 유지한다. 운영자가 직접 SQL로 방/멤버를 수정하거나 구버전 서버가 쓴다면 자동으로 동기화되지 않는다.

## 면접에서 설명할 범위

운영 사고가 아니라 테스트에서 경쟁 조건을 재현하고 대안을 비교한 경험이다. “Redis라서 빠르다”, “분산 락으로 정확히 한 번을 보장했다”, “펜싱 토큰 없이 오래된 모든 요청을 차단했다”라고 표현하지 않는다.

Redis 소유권을 잃은 오래된 작업자와 새 작업자가 동시에 쓰는 상황에서도 진행 중인 참여 1개라는 DB 불변식은 지킨다. 그러나 새 작업자가 참가한 뒤 종료해 점유를 해제하고 나면 과거 요청이 뒤늦게 새 참가를 만드는 것까지 금지하지는 않는다. 요청의 최신성/취소 이후 재실행 금지가 필요하면 요청 상태·멱등 키·자원이 검증하는 단조 증가 fencing 토큰을 별도로 설계해야 한다. 토큰을 발급만 하고 저장소에서 검증하지 않으면 보호되지 않는다.
