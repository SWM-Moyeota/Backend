# 매칭 방 상태 정의 변경과 노쇼 기능 제거 설계

- 날짜: 2026-11-10
- 상태: 승인됨 (황성윤)
- 범위: `matching.party`, `matching.record`, `user`(노쇼 제재), DB 마이그레이션 V37

## 왜 바꾸는가

1차 배포(2026-11-03, 택시 호출 없이 승객끼리 만나 직접 택시를 타는 동승 모드) 뒤에 Party 도메인을 검토한 결과 세 가지가 문제였다.

1. **상태 이름이 뜻과 어긋난다.** `COMPLETED` 가 "정원이 찼다", "15분이 지나 모집이 끝났다", "방장이 약속을 확정했다" 세 가지 뜻으로 쓰였다. `isRecruiting()` 은 모집이 끝난 방에도 참이었다.
2. **노쇼 판정이 사용자에게 불리하게만 작동한다.** 아무도 도착 버튼을 누르지 않으면 같이 탔어도 전원 노쇼가 되고 정산까지 막혔다. 유예도 없고, 심야에는 노쇼 알림조차 가지 않았다. 출시 직후라 이의 신청을 심사할 운영 인력도 없다.
3. **규칙을 PR 마다 덧붙이면서 코드가 흩어졌다.** 같은 검사가 세 가지 방식으로 있고, 같은 상황에 에러 코드가 둘이고, 과도기용 코드에 삭제 조건이 없다.

## 결정

### 방 상태

| 상태 | 뜻 | 들어오는 길 |
|---|---|---|
| `ACTIVE` | 모집 중. **정원이 차도 그대로 ACTIVE** (참여는 `PARTY_FULL` 로 막힌다) | 생성 |
| `COMPLETED` | **약속 확정.** 실시간 방에서 방장이 약속 시간(과 만남 장소)을 확정함 | `confirm` |
| `FINISHED` | 동승 끝. 도착한 멤버가 탄 사람이다 | `depart`, `autoClose`(도착자 있음) |
| `CANCELED` | 동승 없이 닫힘 | 마지막 멤버 나감, 확정 방에서 혼자 남음, 15분·출발 시각까지 혼자, `autoClose`(도착자 없음) |

- 예약 방은 만들 때부터 약속이 있으므로 `COMPLETED` 를 거치지 않는다. `ACTIVE` 에서 바로 닫힌다. 참여는 출발 시각부터 `PARTY_CLOSED` 로 막힌다.
- 불변식: 실시간 방은 `status == COMPLETED` ⇔ `departureAt != null`.
- `PartyStatus` 는 `isOpen()`(ACTIVE·COMPLETED) / `isClosed()` 둘만 둔다. `isRecruiting()`·`isOngoing()` 은 지운다.

### 모집 만료 (15분 / 예약 출발 시각)

- 멤버가 1명이면 `CANCELED`.
- 2명 이상이면 **아무것도 하지 않는다.** 방장이 확정할 때까지 `ACTIVE` 로 두고, 만든 지 1일이 지나면 자동 정리가 `CANCELED` 로 닫는다. 그동안 정원이 남아 있으면 **새 멤버가 계속 들어올 수 있고 목록·후보에도 보인다** — 15분은 "혼자면 접는다"는 기준이지 모집 마감이 아니다.
- 출발 시각이 지난 예약 방은 참여가 `PARTY_CLOSED` 로 막히므로 예약 목록(`GET /matching/reservations`)에서도 뺀다(`departure_at > now`).
- 대상 조회 쿼리가 멤버 2명 이상인 방을 아예 고르지 않는다(매분 같은 방을 잠그지 않기 위해).
- 그래서 SSE `recruiting-closed` 이벤트는 더 나가지 않는다. 이벤트·DTO·notifier 메서드를 지운다.

### 약속 확정 (`confirm`)

- 실시간 방의 방장만. 예약 방은 `NOT_REALTIME_PARTY`.
- 약속 시간은 **확정하는 지금부터 5분 이상 1시간 이하.** "지금"은 안 된다 — 확정 직후 도착·출발을 눌러 남을 떨궈 내는 길을 막는다. 1분 시계 오차 허용은 없앤다. 앱은 가장 짧은 선택지를 5분보다 조금 넉넉하게(예: 6분) 둔다.
- **만남 장소(출발지)를 함께 바꿀 수 있다.** 채팅으로 정한 "2번 출구 버스정류장"을 출발지로 갱신하면 도착 판정(출발지 100m)이 실제 만남 장소를 기준으로 한다. 목적지는 바꾸지 못한다 — 바꾸면 경로·요금을 다시 구해야 하고, 원래 목적지를 보고 들어온 멤버가 불리해진다.
- 장소 필드는 선택이다. 비어 있으면 기존 출발지를 유지한다(11-03 출시 앱은 시간만 보낸다).
- 확정하면 `ACTIVE → COMPLETED`. SSE `confirmed` 에 출발지 좌표·이름을 함께 싣는다.
- 출발지를 얼마나 멀리 옮길 수 있는지 **거리 한계는 두지 않는다**(서비스 지역 검사만). 채팅으로 합의한 장소를 방장이 그대로 옮기는 기능이고, 멤버는 확정 뒤에도 나갈 수 있다.
- 출발지 경로 문자열(`route`)·예상 요금·시간은 실시간 방 생성 때 네이버로 계산한 값이다. 출발지가 움직여도 다시 계산하지 않는다 — 미리보기용 값이고 정산은 실제 요금을 쓴다.
- 채팅방 이름(`chat_room.departure_place`)은 방을 만들 때 복사한 값이라 확정으로 출발지 이름이 바뀌어도 따라가지 않는다. 범위 밖(후속)으로 둔다.

### 나가기 (`leave`)

- 열린 방(ACTIVE·COMPLETED)이면 언제든 나갈 수 있다. 확정 방·예약 방에서도 된다. `CANNOT_LEAVE_CONFIRMED_PARTY` 는 지운다.
- 단, **출발지 도착을 누른 멤버는 나갈 수 없다**(`ARRIVED_MEMBER_CANNOT_LEAVE`). 같이 탄 뒤 방장이 출발을 누르기 전에 나가 정산 대상에서 빠지는 길을 막는다(리뷰 반영).
- 마지막 멤버가 나가면 `CANCELED`. **확정한 실시간 방(`COMPLETED`)에서 나가 1명만 남아도 `CANCELED`** — 약속이 잡힌 뒤라 더 모을 수 없고, 혼자서는 출발할 수 없는 방을 하루 동안 열어 둘 이유가 없다.
- 예약 방은 다르다. 출발 전에 한 명이 나가 혼자 남아도 `ACTIVE` 로 두고 다시 모은다. 출발 시각까지 혼자면 모집 만료가 닫는다(구현자 판단: 출발 3일 전 예약 방이 한 명 나갔다고 취소되면 남은 사람이 손해다).
- 방장이 나가면 가장 먼저 합류한 사람이 승계한다(기존 규칙).

### 도착·출발

- 도착(`arrive`)은 그대로. 약속 10분 전부터, 출발지 100m 안. 도착한 멤버가 정산 대상(`riderIds`)이다.
- 출발(`depart`)은 **방장만** 누른다. 약속 시간 뒤, 방장이 도착한 상태, 멤버 2명 이상. 누르면 `FINISHED`.
- 도착하지 않은 멤버는 정산 대상(`riderIds`)·탑승 기록·탑승 횟수에서 빠진다. 아무 불이익이 없다. 도착 기록이 없는 옛 FINISHED 방(출시 전)은 멤버 전원을 탄 것으로 센다 — 새 규칙으로 FINISHED 가 된 방에는 도착자가 반드시 있으므로 "도착자가 있으면 도착자만, 없으면 전원"으로 옛 기록을 지킨다(리뷰 반영).
- 출발 재촉 푸시는 도착한 멤버 전원이 아니라 **방장에게** 보낸다.

### 자동 정리 (`autoClose`)

- 대상: 열린 방 중 **약속이 있으면 약속 시간 + 1일**, 약속이 없는 실시간 방은 **만든 지 1일.** (지금은 확정한 실시간 방도 만든 시각 기준이라, 하루 동안 멤버가 다른 방에 못 들어가는 문제가 있었다.)
- 결과: 약속이 없거나 혼자면 `CANCELED`. 도착자가 있으면 `FINISHED`(탑승 기록 남김), 없으면 `CANCELED`.
- 조회와 잠금 사이에 닫힌 방은 예외가 아니라 결과 객체(`skipped`)로 돌려준다. 스케줄러의 `catch` 로 정상 흐름을 처리하지 않는다.
- 1일은 설계값이다. 줄이려면 상수 하나(`CompletedPartySweeper.AUTO_CLOSE_AFTER`)만 바꾼다.

### 노쇼 제거

- `matching.noshow`, `user.sanction`, `user.api.NoShowPenalty`, 노쇼 알림, 이용 제한(`NO_SHOW_RESTRICTED`), 이의 신청, 운영자 API 를 모두 지운다.
- 운영자 토큰 체인(`OperatorTokenFilter`, `/api/v1/operator/**`)도 지운다 — 쓰는 API 가 없어진다. 다음 운영자 기능이 생기면 그때 다시 만든다. 설정 `moyeota.operator.token` 도 함께 지운다.
- DB(V37): `user_no_show`, `no_show_objection` 테이블, `users.no_show_count`·`no_show_count_updated_at`·`restricted_until`, `user_match_room.no_show_at`·`no_show_voided_at` 을 지운다. V26·V27·V34 파일은 dev 에 적용돼 있으므로 남긴다.
- 노쇼 스택은 main(운영)에 올라가지 않았다. 운영 데이터 이전은 없다.

### 구버전 호환 코드 정리

지우는 것과 이유:

| 대상 | 이유 |

### 코드 모양 규칙 (Party 애그리거트)

새 사람이 메서드 첫 몇 줄만 보고 무엇을 검사하는지 알 수 있어야 한다.

1. 공개 메서드는 같은 순서로 검사한다: 멤버 → 방장 → 방 열림 → 방 종류·확정 → 인원 → 시간 → 행위자 상태.
2. 같은 조건은 헬퍼 하나로: `findMember`, `ensureHost`, `ensureOpen`, `ensureConfirmed`, `hasCompanion`, `arrivedMembers`. 같은 상황에는 에러 코드 하나(닫힌 방은 `PARTY_CLOSED`).
3. 상태 대입은 전이 메서드 안에서만 한다. `PartyStatus` 주석에 전이 표를 둔다.
4. 지금 시각은 인자(`now`)로 받는다. 도메인 안에서 `Instant.now()` 를 부르지 않는다.
5. 정상적인 건너뛰기는 결과 객체로, 예외는 규칙 위반에만.
6. 주석은 "왜 이 규칙인가"와 "바꾸면 같이 바꿀 곳"만 적는다. 코드를 다시 풀어 쓰지 않는다.
7. 들여쓰기는 스페이스 4칸(파일 안에서 섞지 않는다).
8. 운영 코드에서 부르지 않는 메서드·오버로드·결과 타입은 "나중에 쓸지 모른다"는 이유로 남기지 않고 지운다. 테스트만 쓰는 것은 테스트 헬퍼로 옮긴다.

## 밖에 미치는 영향

- **iOS**: 정원이 차도 `status` 가 `ACTIVE` 다. 확정 방에서 나가기 버튼이 보여야 한다. `recruiting-closed` 는 오지 않는다. `confirmed` 에 출발지 필드가 추가된다. 노쇼 기록·이의 신청 화면과 403 처리는 지운다. `/finish` 는 404 가 된다. 약속 시간 선택지에서 5분 미만을 뺀다.
- **dev DB**: V37 이 노쇼 테이블·컬럼을 지우고, 미확정인데 `COMPLETED` 인 방을 `ACTIVE` 로 되돌린다.
- **운영 DB**: 노쇼 스택이 아직 없으므로 V26~V37 이 한 번에 적용된다. 파괴적 변경 전 수동 스냅샷 규칙을 따른다.

## 작업 위치

`feature/sweeper-cron` 브랜치의 커밋 안 된 수정(Party 일부 반영, faresplit enum 패키지 이동·이름 정리, 정리 스케줄러 cron 변경) 위에서 이어 간다. faresplit 변경은 첫 커밋으로 따로 묶어 PR 을 나눌 수 있게 한다.

## 범위 밖 (후속)

- 확정으로 바뀐 출발지 이름을 채팅방 이름에 반영.

- 확정 방에서 혼자 남아 취소될 때 남은 사람에게 푸시(지금은 SSE `closed` 만).
- 실시간 방이 15분 뒤에도 혼자일 때 근처 방·예약 방 대안 안내.
- 알림 기록 필드 3개(`reminderSentAt`, `meetingNotifiedAt`, `departureReminderCount`)를 별도 테이블로 묶기.
