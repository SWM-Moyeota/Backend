# 사전결제·취소 검증 기능 개발 기록

## 이 문서의 목적

대화와 개발 과정에서 **어떤 문제를 고민했고, 왜 특정 방향을 선택했으며, 무엇을 수정하고 확인했는지** 기록한다. 결과뿐 아니라 그 결과에 도달한 이유를 남겨 이후 코드를 다시 읽을 때 이해할 수 있도록 한다.

- [전체 설계 및 작업 계획](payment-verification-plan.md): 구현할 기능, 작업 순서, 체크리스트와 완료 기준
- 이 문서: 실제로 진행한 논의, 결정과 미결정 사항, 코드 변경 및 검증 기록

제안한 설계와 확정한 결정을 구분한다. 논의만 한 내용을 구현 완료로 기록하지 않는다. 이후 방향이 바뀌면 이전 판단을 지우기보다 변경 이유와 새 판단을 추가한다.

## 지속적인 변경 추적 규칙

사용자는 대화하면서 생각과 설계가 바뀌는 과정 자체를 지속적으로 추적하기를 요청했다. 이 기능에 관한 후속 논의와 구현에서도 다음 규칙을 적용한다.

- **계획은 최신 상태, 개발 기록은 판단의 변화 과정**을 보여준다.
- 사용자가 제시한 고민·의도·수정 의견과 어시스턴트의 제안·해석을 구분한다. 명시되지 않은 생각이나 이유를 사용자에게 귀속하지 않는다.
- 새로운 고민, 설계 제안, 확정된 변경, 구현 결과가 생기면 의미 있는 작업 단위로 기록한다. 제안과 미결정 사항도 상태를 명시해 남긴다.
- 설계가 확정되거나 변경되면 계획의 관련 작업·순서·완료 기준·진행 상태를 함께 갱신한다. 아직 논의 중이면 기존 확정 방향과 분리해 미결정 사항으로 표시한다.
- 변경 기록에는 이전 방향, 변경 계기, 새 방향, 선택 이유, 영향을 받는 작업 번호와 코드, 남은 질문을 포함한다.
- 과거 기록을 새 설계로 덮어쓰지 않는다. 판단 변경은 새 기록으로 추가하고, 잘못 기록한 사실은 정정 이유를 남긴다.
- 완료된 코드가 새 설계와 맞지 않으면 계획에 재작업을 표시하고 개발 기록에 수정이 필요한 이유를 남긴다.
- 작업 완료 시 실제 수정 파일과 검증 결과를 기록하고 계획의 체크 상태를 맞춘다. 문서만 바뀐 경우 구현 완료로 표시하지 않는다.
- 문서 상단의 현재 상태와 다음 작업도 최신 논의에 맞게 유지한다.

## 2026-10-27 — 현재 코드 흐름 검토

### 시작한 고민

기본 결제수단에 예상 금액을 결제할 여력이 있는지 확인하기 위해 사전결제 후 취소하는 기능을 만들려고 했다. 결제와 취소 API를 나누어 작성하고 있었으나, 백엔드가 전체 절차를 책임지도록 하나의 API로 연결하고 싶었다.

작업 중인 코드가 섞여 있어 먼저 현재 구현 위치와 앞으로의 흐름을 정리하기로 했다.

### 확인한 현재 구현

- `PaymentMethodService.prePay()`에는 사용자 존재, 방 참여 여부, 예상 요금, 기본 결제수단과 빌링키 조회가 작성되어 있었다.
- 포트원 결제 호출 메서드는 작성 중이었으며 서비스에서 호출하지 않았다.
- 결제 기록 저장과 취소 실행은 연결되지 않았다.
- `Payment`와 `PaymentGroup` 엔티티는 있었지만 검증 결제의 저장·상태 변경 흐름은 미완성이었다.
- 컨트롤러의 중복 메서드·매핑, 미완성 선언, DTO 문법 등 정리가 필요한 부분이 있었다.

이는 당시 작업 트리를 읽어 확인한 내용이다. 빌드나 실제 결제 호출로 검증한 결과는 아니다.

### 논의하면서 명확해진 점

1. 이 기능은 잔액 자체를 조회하는 기능이 아니라, **현재 정해진 금액을 결제할 수 있는지 확인하는 절차**다.
2. 취소 이후 실제 운행 요금을 청구할 때도 결제가 가능하다는 보장은 없다.
3. 취소 대상은 기본 결제수단이 아니라 **이미 실행한 특정 결제 건**이다. 결제 이후 기본 카드가 바뀌더라도 원래 결제를 취소해야 한다.
4. DB 트랜잭션을 롤백해도 외부에서 승인된 결제는 자동으로 취소되지 않는다.
5. 결제 성공 후 취소 실패 또는 서버 종료가 발생할 수 있으므로, 결제 ID와 상태를 저장하고 후속 처리할 수 있어야 한다.

### 제안한 설계 방향

- `PaymentMethodService`는 결제수단 관리에 집중한다.
- `PrePaymentService`가 검증 정보 조회, 결제 기록 생성, 결제 실행을 담당한다.
- `PaymentCancellationService`가 저장된 결제 건의 취소를 담당한다.
- `PortOneClient`는 외부 결제·조회·취소 통신을 담당한다.
- 외부 호출 전후의 DB 저장을 짧은 트랜잭션으로 분리한다.
- 결제 실패와 취소 실패를 구분하고, 결과를 모르는 경우에는 조회로 확인한다.
- 재요청과 서버 중단에도 중복 결제 없이 기존 작업을 이어가도록 한다.

클래스명, 상태 모델, 트랜잭션 구현 방식은 제안 단계이며 아직 코드에 적용하지 않았다.

### 아직 결정하지 않은 사항

- 전체 예상 요금을 검증할지, 사용자 예상 분담금을 검증할지
- 검증을 실행하는 구체적인 시점과 허용할 방 상태
- 처리 중 결과를 클라이언트가 확인하는 방법
- 동일 요청을 식별하는 기준과 재검증 허용 조건
- 검증 결제에 `PaymentGroup`을 사용할지
- 결제·취소 상태를 어떤 필드와 enum으로 표현할지

### 변경 및 확인

- 애플리케이션 코드는 수정하지 않았다.
- 소스 코드와 포트원 공식 결제 API 명세를 읽고 흐름을 검토했다.
- 빌드, 자동 테스트, 실제 결제·취소 호출은 실행하지 않았다.

## 2026-10-27 — 작은 단위로 개발하는 방식 정리

### 시작한 고민

한 번에 전체 코드를 생성하면 동작은 만들어져도 작성된 코드를 이해하기 어렵다. 사용자는 작은 단위로 작업을 요청하고 각 변경을 이해하면서 개발하고 싶다고 설명했다.

### 정한 진행 방식

- 한 번에 클래스 하나 또는 동작 하나 정도의 작업을 진행한다.
- 정책을 먼저 결정하고, 그 정책을 구현하는 코드를 작성한다.
- 각 작업마다 변경 이유, 코드 변경, 요청 처리 흐름, 확인 결과를 설명한다.
- 완료 기준을 확인하고 이해한 뒤 다음 단계로 넘어간다.
- 테스트는 마지막에 몰지 않고 중요한 동작을 추가할 때 함께 진행한다.

### 작업 순서를 이렇게 나눈 이유

| 순서 | 이유 |
|---|---|
| 검증 정책 결정 | 얼마를 언제 검증할지 정해야 코드의 기준이 생김 |
| 기존 코드 정리 | 중복·미완성 코드와 새 기능 구현을 분리해 이해하기 위함 |
| 결제 기록·상태 설계 | 외부 결제 이후 문제가 발생해도 추적할 근거가 필요함 |
| 사전결제 구현 | 정보 조회부터 결제 결과 기록까지 하나씩 연결하기 위함 |
| 취소 구현 및 API 연결 | 원래 결제 건을 기준으로 취소하고 최종 결과를 반환하기 위함 |
| 중복·실패 복구 | 요청 재전송이나 서버 중단에도 백엔드가 작업을 마무리하기 위함 |

- 제안·미결정·확정·구현·검증 상태를 구분하고 두 문서를 함께 갱신한다.

## 2026-10-27 — estimatedFare의 소유와 결제 모듈의 책임 명확화

### 사용자가 설명한 내용

`estimatedFare`는 매칭 모듈의 `Party` 엔티티에 있는 값이며, 결제 측에서 값을 만들거나 계산하는 것이 아니라 읽어오는 값이라고 설명했다.

### 이전 계획에서 바뀐 부분

이전 계획은 예상 요금의 생성·계산 흐름 확인과 검증 금액 계산 구현을 작업으로 표현했다. 이 표현은 결제 모듈이 예상 요금을 산출해야 한다는 의미로 읽힐 수 있었다.

사용자의 설명에 따라 예상 요금의 소유·산출 책임은 매칭 모듈에 있고, 결제 모듈은 해당 값을 조회하고 사용할 수 있는지 검사하는 것으로 정리했다. 기존 코드의 `PartyAccess.findSummary(partyId)` → `PartySummary.estimatedFare()` 경로와도 일치한다.

### 계획 반영

- 01번을 예상 요금 조회와 사용 기준 정리로 변경하고, 출처·조회 경로를 확인 완료로 표시했다.

## 2026-10-27 — READY와 PENDING의 구분 검토

### 사용자의 고민과 이해 과정

사용자는 사전결제 상태를 다섯 가지로 나눈 상황에서 `READY`와 `PENDING`을 모두 둘 필요가 있는지 질문했다. 이후 준비 상태의 의미, 결제 상태 저장의 의미, 기존 사용자·방·카드 검증 순서와의 관계, 실제로 대기 단계가 필요한 사례를 차례로 확인했다.

사용자는 최종적으로 검증·조회 단계에서는 결제 기록을 만들지 않고, 그 이후 결제 처리를 시작하면서 곧바로 `PENDING`을 저장하므로 현재 모여타 흐름에 `READY`가 필요하지 않다는 이해를 제시했다.

### 정리한 설계 방향과 이유

- 사용자 검증 → 방 참여 검증 → 예상 요금 조회·검증 → 기본 결제수단 조회·검증 순서를 유지한다.
- 이후 기존 `payment` 테이블에 결제 한 건의 행을 `PENDING`으로 저장·커밋하고 포트원에 요청한다. 요청마다 테이블을 만드는 것이 아니다.
- 예약 시각, 사용자 조작, 별도 작업자 등을 기다리는 준비 단계를 현재 요구사항에 두지 않으므로 `READY`는 생략한다.
- `PENDING`은 결과 미확정 상태다. 저장 직후 외부 호출 전에 서버가 중단될 수도 있으므로, 외부 요청이 전달되었다는 증거로 사용하지 않는다.
- 타임아웃을 결제 실패로 단정하지 않고 기존 결제 ID로 상태를 조회한다.
- 향후 예약·큐 기반 처리로 바뀌면 실행 대기 상태의 필요성을 다시 검토한다.

### 계획 반영과 남은 사항

- 계획 09번에 초기 상태 방향과 의미를 기록하고, 16번에 검증 후 `PENDING` 기록 생성 순서를 반영했다.
- 상태명에 `VERIFICATION_` 접두사를 사용할지, 취소 상태를 별도로 둘지는 이번 논의에서 확정하지 않았다.
- 문서만 수정했다. enum과 애플리케이션 코드는 아직 변경하지 않았으며 실행 테스트도 하지 않았다.

## 2026-10-27 — 결제 API의 ERD 범위 제공

### 사용자가 제공한 설계 자료

사용자는 아래 네 테이블이 이번 결제 API를 만들면서 다룰 ERD라고 설명했다. PK는 이미지의 열쇠 표시를 옮긴 것이며, FK 제약·null 허용·기본값·문자열 길이는 명시되지 않았다고 밝혔다. 아래는 제공된 원문 기준이다.

| 테이블              | 컬럼과 타입                                                                                                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payment`        | `id` Long PK, `pg_payment_id` VarChar, `user_id` Long, `payment_group_id` Long, `payment_method_id` Long, `amount` Integer, `status` ENUM, `type` ENUM, `order_name` Varchar, `currency` ENUM, `fail_code` Varchar, `created_at` LocalDateTime, `updated_at` LocalDateTime |
| `payment_group`  | `id` Long PK, `match_id` Long, `taxi_driver_id` Long, `passenger_count` Integer, `status` Enum, `created_at` LocalDateTime, `updated_at` LocalDateTime                                                                                                                     |
| `payment_log`    | `id` Long PK, `payment_id` Long, `amount` Integer, `status` ENUM, `type` ENUM, `fail_code` Varchar, `created_at` LocalDateTime, `updated_at` LocalDateTime                                                                                                                 |
| `payment_cancel` | `payment_id` Long PK, `cancel_at` LocalDateTime, `cancel_reason` VarChar, `created_at` LocalDateTime, `updated_at` LocalDateTime                                                                                                                                           |

원문의 enum은 다음과 같다.

- `payment.status` 별도 메모: `VERIFICATION_PENDING`, `VERIFICATION_READY`, `VERIFICATIOIN_PAID`, `VERIFICATION_FAILED`, `VERIFICATION_CANCELED`
- `payment.type`, `payment_log.type`: `VERIFICATION`, `MAIN`
- `payment.currency`: `KRW`, `USD`, `JPY`
- `payment_group.status`: `PENDING`, `PARTIALLY_FAILED`, `COMPLETED`, `CANCELLED`
- `payment_log.status`: `PAID`, `FAILED`, `CANCELED`

### 기존 논의와 대조한 사항

- 제공된 ERD에 `READY`가 있어도 앞서 논의한 생략 방향을 철회했다고 해석하지 않는다. 원문과 변경 방향을 별도로 보존한다.
- `VERIFICATIOIN_PAID`는 원문 표기이며 오타 후보로 남긴다. 취소 상태 철자 통일 및 상태명 접두사 사용도 구현 전 정리 대상이다.
- `payment_cancel.payment_id`가 PK이므로 취소 기록은 결제당 최대 한 행이다. 재시도별 이력을 별도 행으로 남기려면 추가 설계가 필요하다.
- 관계를 나타내는 컬럼 이름이 있다고 FK 제약이 확정된 것은 아니다.
- 기존 코드의 `Payment`에는 취소 필드가 있고 `PaymentGroup`에도 제공된 ERD와 다른 필드가 있으므로, 코드 변경 전에 역할과 매핑을 비교해야 한다.

### 새로 명확히 해야 할 설계

- 검증 결제 시 `payment_group`을 언제 만들거나 재사용하는가? 검증 취소가 그룹 전체 취소를 의미하는 것은 아니므로 그룹 상태 기준은 별도로 정한다.
- `payment_log`는 상태 변경 이력인가, 개별 결제 시도 이력인가? 제공된 상태 목록에는 `PENDING`이 없어 기록 범위도 정해야 한다.
- `payment_cancel`은 취소 요청 시 생성하는가, 완료 시 생성하는가? 취소 진행·실패·재시도 정보는 어디에 저장하는가?
- `MAIN` 결제 상태는 어떻게 표현하는가? 현재 별도 상태 메모에는 검증용 이름만 제시되어 있다.

### 반영 및 검증 범위

- 계획에 네 테이블의 역할과 미결정 사항을 추가하고 08·11·12·19·22번 작업에 반영했다.
- 자료 제공은 구현 지시로 확대하지 않았다. 문서만 수정했으며 엔티티·마이그레이션·테스트는 변경하거나 실행하지 않았다.

## 2026-10-27 — 공통 결제 상태 네 가지와 결제 타입 두 가지 확정

### 고민과 결정 과정

사용자는 검증 결제 상태에 MAIN 결제용 상태도 추가해야 하는지 질문했다. 어시스턴트는 이미 `type`으로 결제 목적을 구분하므로 상태를 공통으로 사용하면 유형 정보를 중복하지 않고 잘못된 유형·상태 조합도 줄일 수 있다고 제안했다.

이어서 MAIN에서도 READY가 필요한지 검토했다. 준비 후 즉시 실행하는 흐름에서는 생략 가능하며, 향후 예약·큐 기반 처리를 도입한다면 대기 상태의 필요성을 다시 판단하기로 설명했다.

사용자는 정상 검증 절차의 취소를 CANCELED로 표현하면 임의 취소처럼 보일 수 있다는 고민도 제시했다. 결제 관점에서는 취소 완료가 맞고, 검증 절차 관점에서는 정상 완료일 수 있으므로 서로 다른 의미로 구분했다. 취소 목적은 결제 타입과 취소 사유로 나타내며, API에서 검증 완료를 표현하는 방식은 별도 설계 대상이다.

사용자가 최종적으로 상태 네 가지와 결제 타입 두 가지를 사용하는 방향을 요청했다.

### 확정한 내용과 실제 변경

- `PaymentStatus`: `PENDING`, `PAID`, `FAILED`, `CANCELED`.
- `PaymentType`: `VERIFICATION`, `MAIN`.
- 상태에 `VERIFICATION_` 또는 `MAIN_` 접두사를 붙이지 않는다.
- 기존 `PaymentStatus.java`에서 `READY`를 제거했다. `PaymentType.java`는 이미 요구한 두 값이라 변경하지 않았다.
- 계획 09번과 ERD 해석을 최신 결정으로 갱신했다. 과거 ERD 원문과 당시의 미결정 기록은 보존했다.

### 검증과 범위

- 소스 검색에서 `PaymentStatus.READY` 참조가 없고 `Payment` 생성 시 `PaymentStatus.PENDING`을 사용함을 확인했다.
- 애플리케이션 전체 빌드·테스트는 실행하지 않았다. 현재 별도의 미완성 코드 정리 작업은 남아 있다.
- 취소 진행·실패·재시도 기록 설계 및 `payment_group` 상태 변경은 이번 작업에 포함하지 않았다.

## 2026-10-27 — 방별 결제 그룹 공유와 데이터 생성 순서 확정

### 사용자가 확정한 내용

1. 같은 매칭방의 사전결제와 MAIN 결제를 하나의 그룹으로 묶는다. 사용자 n명에 대해 두 유형의 결제가 있으므로 기본적으로 결제 테이블에 2n행이 생긴다.
2. 생성 순서는 결제 그룹 → 결제 → 결제이력이다. 먼저 그룹 ID를 만들고 결제에서 그 ID를 연결한다.
3. 방 하나에 그룹 하나를 두고, 첫 사전결제를 시작할 때 생성한다.

### 이전 설계에서 확정된 부분

이전에는 검증 결제에 그룹을 사용할지와 생성 시점이 미정이었다. 이번 결정으로 VERIFICATION과 MAIN이 동일 그룹을 공유하고, 최초 검증 시 그룹을 생성한 뒤 이후 결제에서 재사용하는 것으로 확정했다.

여기서 생성하는 것은 요청마다 새 테이블이 아니라 각 테이블의 데이터 행이다. 2n은 두 유형의 결제가 모두 만들어진 시점의 기본 구조로 기록하며, 첫 요청 때 미래 MAIN 결제까지 미리 생성하도록 확대 해석하지 않는다.

### 아직 결정하지 않은 내용

- 결제이력은 상태 변경마다 생성하는지, 실행 시도마다 생성하는지와 최초 생성 시점.
- 실패·재검증·재시도에서 기존 결제 행을 갱신할지와 개별 시도 식별 방법. 기본 2n 구조를 유지하려면 이력 모델과 함께 정해야 한다.
- 동시 첫 요청에서도 그룹이 하나만 생성되도록 하는 DB 제약과 충돌 처리.
- 그룹 생성 시 기사·탑승 인원이 확정돼 있는지와 미확정 값 처리.
- 검증 결제의 정상 취소와 MAIN 결제 결과를 그룹 상태에 반영하는 기준.

### 반영 및 검증 범위

- 계획의 ERD 역할 설명과 08번을 갱신하고, 다음 논의 대상을 결제이력 기록 단위로 정리했다.
- 이전 미결정 기록은 당시 판단을 보존하고, 현재 상태 표를 갱신했다.
- 이번에는 문서만 변경했다. 엔티티·저장소·DB 제약 구현이나 실행 테스트는 진행하지 않았다.

## 2026-10-27 — 기사 미배정 상태의 결제 그룹 생성

### 사용자의 고민과 추가 정보

사용자는 `payment_settlement`와 `payment_group` 중 기사 ID를 어디에 둘지 고민했다. 이어 사전결제는 방만 생성되고 기사가 아직 매칭되지 않은 시점에 실행되므로, 그룹의 기사 ID를 나중에 추가하면 되는지 확인했다.

제공된 정산 ERD는 `payment_group_id` Long PK, `total_fare` Integer, `fare` Integer, `remaining_balance` Integer, `platform_charge` Integer, `created_at` LocalDateTime, `taxi_driver_id` Long이다. `remaining_balance`는 나누어 떨어지지 않는 금액과 관련된 설명이며, 계산·배분 공식과 FK·null·기본값은 확정되지 않았다. 기사 ID의 배치는 이번 논의 대상이므로 원문의 양쪽 배치를 확정으로 취급하지 않는다.

### 정리한 방향과 이유

- 첫 사전결제 때 그룹이 필요하지만 기사는 아직 없으므로, `payment_group.taxi_driver_id`는 null을 허용한다.
- 기사 배정이 확정된 이후 그룹에 ID를 채운다. 결제 상태 자체와 기사 배정은 별개이므로, 임의의 결제 상태 전환을 배정 근거로 삼지 않는다.
- 기사 배정 이벤트를 받을지 또는 확정된 매칭 정보를 조회할지는 아직 구현 방식이 정해지지 않았다.
- 배정 취소·재배정 시 갱신 규칙과 실제 운행 기사 확정 시점은 추가 설계가 필요하다.
- 정산에 별도의 지급 대상 기사 스냅샷이 필요한지는 정산 역할을 정할 때 판단한다. 지금 양쪽에 동일 ID를 중복 저장하도록 확정하지 않는다.

### 반영 및 확인 범위

- 계획의 그룹 생성 전제와 08번을 갱신했다. 첫 사전결제 시 기사 미배정이라는 기존 미결정 사항을 해소했다.
- 현재 엔티티의 기사 필드 및 DB 제약을 수정한 것은 아니다. null 허용과 컬럼 매핑은 이후 구현에 반영해야 한다.
- 이번에는 문서만 변경했으며 실행 테스트는 하지 않았다.

## 2026-10-27 — 배정 완료 이벤트 연동을 구현 계획에 추가

### 확인한 사실과 사용자의 요청

사용자는 잘못 붙여 넣은 ERD 설명 대신, 기사 콜 수락 시 `party.taxi_driver_id`가 저장되는 코드 흐름을 기준으로 논의하려는 것이라고 정정했다.

소스 확인 결과 `DispatchService.acceptCall()`이 수락 조건을 검사하고 `PartyAccess.assignDriver()`를 호출한다. `Party.assignDriver()`는 방의 MATCHING 상태와 기사 미배정을 확인한 뒤 기사 ID 및 `DRIVER_ASSIGNED` 상태를 설정하며, `PartyAccessService`가 저장한다. 정상 커밋된 배정 사실을 결제 모듈에 전달하는 연결은 별도 구현이 필요하다.

어시스턴트가 배정 완료 이벤트 수신 방식을 제안했고, 사용자는 이것도 결제 API 개발에 필요한 절차이므로 계획에 명시하도록 요청했다.

### 설계 방향과 구분

- 콜 수락 저장이 정상 커밋된 뒤 결제 모듈에서 배정 완료 사실을 처리한다.

## 2026-10-27 — 서비스가 성공을 보장하는 컨트롤러 골격 구현

처음에는 서비스가 성공·실패·처리 중을 모두 반환하고 컨트롤러가 `isPaid()`로 분기하는 방식을 제안했다. 사용자는 성공 판단과 예외 처리를 서비스에 모으고 컨트롤러에는 큰 흐름만 두기를 원했다. 두 방식의 차이를 비교한 뒤, 서비스가 성공 시에만 정상 반환하고 나머지는 업무 예외를 던지는 방향으로 정리했다.

사용자가 코드 반영을 요청하여 현재 빈 `PaymentController`, `PaymentService` 클래스에 구현을 추가했다.

### 실제 변경

- `PaymentController.verifyPaymentCapability`: 결제 서비스 호출 → 반환된 내부 결제 ID로 취소 서비스 호출 → 결과 응답. 컨트롤러의 성공 판단 분기와 예외 포착은 없다.
- 기존 결제수단 컨트롤러의 중복 사전결제·취소 매핑을 제거하고 카드 관리 기능은 유지했다.
- 기존 사용자·방·금액·기본 카드 조회 로직을 `PaymentMethodService`에서 `PaymentService`로 이동했다. 예상 금액 null·0 이하를 업무 예외로 처리했다.
- 결제 결과 DTO의 record 문법과 타입을 정리하고, 취소 완료 후 반환할 `PaymentVerificationResponse(paymentId, verified)`를 추가했다.
- `PaymentCancellationService` 골격을 추가했다.
- 실제 결제·취소를 한 번에 구현하지 않았다. 현재 두 서비스의 미구현 구간은 501 업무 예외를 던지며, 결제를 하지 않고 성공을 반환하지 않는다. 준비 조회를 감싼 읽기 전용 트랜잭션은 향후 외부 결제 연결 시 재구성해야 한다.

- 외부 포트원 호출은 하지 않는다. 이 검증은 컨트롤러 계약과 기존 카드 관리 회귀 검증이며 결제 연동 성공을 의미하지 않는다.

## 2026-10-27 — 사용자 한 명 조회를 명시적인 단일 조회로 변경

### 사용자의 고민과 요청

사용자는 사용자 한 명을 확인하는데 왜 ID 목록과 Map을 사용하는지 질문했다. 기존에는 여러 명 조회 API를 재사용하려고 한 개짜리 목록을 전달했지만, 한 명 조회 의도를 드러내는 메서드가 더 명확하다고 판단해 단일 조회로 바꾸도록 요청했다. 이 변경은 기존 방식이 잘못된 결과를 낸다는 뜻은 아니다.

### 실제 구현 위치와 흐름

기존 코드에는 `findMemberSummary`가 없었다. 이번에 다음 경로를 추가했다.

```text
PaymentUserResolver.publicIdOf(userId)
  → UserAccess.findMemberSummary(userId): 모듈 간 조회 계약
  → UserAccessService.findMemberSummary(userId): 실제 서비스 구현
  → Users.findOptionalById(userId): 저장소 계약
  → UserJpa.findOptionalById(userId): 저장소 구현
  → UserRepository.findById(userId): Spring Data JPA 단일 조회
```

- 없는 사용자는 Optional.empty로 반환하고, 결제 모듈에서 PAYMENT_USER_NOT_FOUND로 변환한다.
- 기존 `Users.findById()`는 없는 사용자에 예외를 던지는 계약이므로 그대로 유지하고, Optional 반환용 메서드를 별도로 추가했다.
- 단일·다건 요약 변환은 공유해 탈퇴자의 표시 이름·이미지·배지 처리 방식을 유지했다. 활성 사용자 검증 정책을 새로 추가한 것은 아니다.
- 기존 다건 조회 호출자는 유지했다. 결제 관련 테스트를 단일 조회로 바꾸고, 인터페이스를 구현하는 테스트용 객체도 새 메서드에 맞췄다.
- 검증: 테스트용 구현체의 메서드 위치 오류를 수정한 뒤 컴파일 및 관련 테스트 46개가 통과했다. `git diff --check`도 통과했다. 외부 서비스 호출은 하지 않았다.

- `PaymentService`를 기존 빈 클래스로 돌리고 자동 작성한 조회·검증·취소 메서드를 제거했다.
- `PaymentUserResolver`, 새 컨트롤러·서비스 테스트를 삭제했다.
- 사용자 모듈의 단일 조회 확장과 관련 테스트 수정을 되돌렸다.
- 카드 관리 서비스의 기존 사용자 조회 헬퍼를 복원해 기존 카드 관리 기능을 유지했다. 사용자가 작성한 카드 관리·엔티티·포트원 초안 등은 일괄 초기화하지 않았다.
- 임시 501 오류 코드와 컨트롤러의 501 설명을 제거했다.
- 컨트롤러가 호출하는 서비스 메서드는 아직 없으므로 현재 컴파일 불가 상태다. 이를 막기 위한 임의의 서비스 구현이나 가짜 성공 응답을 다시 추가하지 않았다. 이번에는 빌드·테스트를 실행하지 않았다.
- 이전 개발 기록은 당시 작업 내역으로 보존하며, 현재 구현 상태는 이 기록이 우선한다.

## 이후 작업 기록 양식

아래 양식을 복사해 작업 단위로 기록한다. 문서 정리만 한 경우에는 코드 변경·테스트가 없었다고 명시한다.

```markdown
## YYYY-MM-DD — 작업 번호 및 제목

### 시작한 고민

- 무엇이 불명확하거나 문제가 되었는가?
- 이번 작업에서 해결하려는 범위는 어디까지인가?

### 확인한 사실

- 기존 코드나 실행 결과에서 무엇을 확인했는가?
- 확인한 사실과 추측을 구분한다.

### 검토한 선택지와 판단

- 어떤 방법을 검토했는가?
- 어떤 방향을 선택했고 이유는 무엇인가?
- 아직 제안 단계이거나 결정하지 않은 사항은 무엇인가?
- 사용자가 직접 밝힌 고민과 어시스턴트의 제안은 각각 무엇인가?
- 이전 설계에서 무엇이 왜 바뀌었고, 계획의 어떤 작업 번호에 영향을 주는가?

### 변경한 내용

- 변경한 파일과 핵심 동작
- 변경 전후의 차이
- 코드 변경이 없다면 그 사실

### 코드 이해 메모

- 요청 한 건이 어떤 클래스와 메서드를 거치는가?
- 중요한 필드, 상태, 트랜잭션은 어떤 역할을 하는가?

### 검증 결과

- 실제로 실행한 검사·테스트와 결과
- 실행하지 않은 검사와 남아 있는 한계
- 로컬·모의 결제사·외부 테스트 환경을 구분

### 남은 고민과 다음 작업

- 미결정 사항 또는 발견한 문제
- 다음에 진행할 작업 번호와 이유
```
