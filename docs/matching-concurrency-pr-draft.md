# 사용자 행 잠금과 현재 참여 제약으로 중복 동승 참가 방지

기준 브랜치: `develop`. 작업 브랜치: `feature/matching-db-concurrency`.

## 문제

동일 사용자가 서로 다른 방에 동시에 참가하면 각 방의 행 잠금은 충돌하지 않아 진행 중인 방이 두 개 생길 수 있다. 테스트에서 기존 조회 후 저장 알고리즘의 경쟁 조건을 재현했다. 정원 초과와 사용자 중복 참여를 각각 보호해야 한다.

## 분석

DB 사용자 행 잠금, Lettuce 직접 구현, Redisson, ZooKeeper의 잠금 수명·대기 방식·장애와 유지보수 비용을 비교했다. Redis 락도 만료·연결 단절 후 이전 작업자의 DB 쓰기를 자동 취소하지 않는다. 최종 정합성은 DB 트랜잭션, 현재 참여 사용자 PK, 방 행 잠금으로 방어한다. Redisson은 Redlock과 다르며 ZooKeeper/Redlock은 문서 검토 대상이다.

## 실행

사용자 행을 먼저 잠근 뒤 참가 여부를 검사하고 방을 잠근다. 잠금은 트랜잭션 종료까지 유지하며 DB 잠금 대기 제한을 설정한다.

현재 참여 테이블을 별도로 두어 종료된 참가 이력과 활성 참가 제약을 분리했다. 외부 경로 조회는 잠금·트랜잭션 밖으로 옮겼다. 퇴장·종료 등 저장 시 현재 참여를 함께 동기화한다.

## 결과 및 검증

DB 브랜치 전체 테스트 450개 통과. 실제 PostgreSQL·Redis로 중복 참가, 생성/참가 경쟁, 마지막 자리, 롤백 및 재참가를 검증했다. 성능 실험은 작업자 16개·96요청·3회이며 정상 거절을 포함한 완료 처리량이다. DB/Redis 비교의 동일 사용자 경합에서 관측 DB 연결은 16→1로 줄었지만 Redis의 p95는 증가했다. 추가 Lettuce/Redisson 비교의 동일 사용자 p95 중앙값은 159.53/114.73ms였다. 로컬 단일 JVM 결과를 운영 성능으로 일반화하지 않는다.

MVP 우선 추천은 DB 방식이다. Redis가 필요해지면 자동 갱신·소유권 검사·알림 대기 유지보수 비용을 고려해 Redisson을 선택한다. 구현 개수가 아니라 경쟁 조건 재현→불변식 정의→대안 실험→선택을 PAAR 경험으로 설명한다. 운영 장애를 해결했다고 표현하지 않는다.

상세 비교·재현 명령·측정 한계는 [동시성 설계 문서](matching-concurrency.md), 원시 결과는 [실험 결과](matching-concurrency-results.json)에 있다.

## 적용 조건

두 브랜치는 대체안이며 그대로 함께 병합하지 않는다. V7 적용 전 기존 활성 중복 참여를 확인하고 새 테이블을 쓰지 않는 구버전 노드와의 혼재를 방지해야 한다. 다른 미병합 V7과 충돌하면 적용 전에 번호를 조정한다. fencing이나 HTTP 멱등 응답 저장은 구현하지 않았다. 새 참여가 종료된 후 과거 요청이 뒤늦게 실행되는 최신성 문제는 별도 설계 대상이다.
